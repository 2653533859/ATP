## 3. 当前三条主线

### 3.1 共用产品与执行内核

共同业务链路应稳定为：

需求/知识 → 用例/测试资产 → 套件/计划 → 执行 → 报告/失败证据 → 缺陷/经验。

共用业务规则、数据模型和执行器；模式配置负责数据库、文件与投递方式。领域服务承载可复用规则，API 做权限、输入与编排，Worker 承载长期执行。新增助手写操作也应调用这些服务。

当前基础设施对应关系：

| 维度 | Windows 本地 | Linux 服务器 |
| --- | --- | --- |
| 人员与项目 | 单用户、单项目 | 多用户、多项目与角色 |
| 数据 | SQLite 及版本迁移 | PostgreSQL 及 Alembic |
| 文件 | 本地目录 | MinIO |
| 投递 | SQLite 持久单机队列 | Redis/Celery Worker |
| 组执行 | 套件/手动计划串行 | 可配置并发与队列路由 |
| 运维 | 本机启动、停止、备份、恢复与转移 | 镜像、Chart、迁移、监控、回滚与发布证据 |

两套数据、账号、模型配置与密钥独立，不自动同步。切换模式是选择入口，不是数据库迁移或双向同步。

### 3.2 Windows 本地版

代码接入范围包括 API/Web/Android、Web 录制、协议用例、手动套件/计划、环境/数据集/Web 资产、需求/缺陷/知识、AI 配置与生成、Hermes 和单机性能。

当前边界：

- 本地组任务串行；停止通常在当前子任务结束后生效。计划不支持本地 Cron/Webhook，性能不支持远程节点或分片。
- 已有 API/Web 手动运行、部分文件/报告、排队恢复及同机备份恢复的历史证据。
- 扩展后的混合套件、手动计划、协议、真实模型、单机性能与 Android 真机需要补充真实验收。
- 静态前端运行不需要 Vite/Node 进程，但安装、构建与后端仍需要环境依赖；目前不是已验证的免安装可执行包。
- 异机恢复、双会话切换、SQLite 升级与服务器兼容回归仍是 M8/M7 的收口工作。

### 3.3 Linux 服务器与发布

服务器范围是单节点 K3s。当前计划记录已完成 Web/协议/Android 单节点业务、性能短压与取消、观测、权限分离和迁移/恢复演练。

仍开放：

1. 代表性业务流量的连续 7/14 日 SLO、告警与 Flower 长期趋势。
2. 绑定最终提交 SHA，构建完整源码不可变镜像，确认迁移、Chart 差异与回滚。
3. 同一版本下的质量、安全、集成、真实环境证据及发布索引。

历史记录到 9 月 29 日，不能据此确认 10 月 7 日服务器仍健康，也不能因时间已过去而自动判定 SLO 通过。

多节点高可用、跨节点调度、跨主机 MinIO 灾备、iOS/Appium、外部通知与外部缺陷供应商正式验收目前属于后续增强或技术预览，不应重新成为当前版本的无条件阻塞项。

## 4. 主要未收口问题

| 问题 | 当前事实 | 对开发路线的影响 |
| --- | --- | --- |
| 提交与投递之间存在中断窗口 | SuiteRun 与 HermesAction 先提交，再调用队列；相同编号重试只返回原运行 | 幂等不等于可靠投递，应优先建立持久投递意图和核对机制 |
| 命令与资源的身份需要加固 | 命令只保存整数资源编号；创建套件重放未核对创建身份，SQLite 删除最高编号后可能重用编号 | 静态代码推断，未执行重演；命令服务应保存并核对资源身份，避免返回后建同编号资源 |
| 助手动作能力不均衡 | 八个入口已接入，服务端命令记录只覆盖套件创建与执行 | 先稳定套件完整闭环，再复用命令服务推广；避免直接复制到更多 API |
| 新操作面板建议与确认未完整持久化 | 原 Hermes 已有会话草稿/确认 API；新增八类操作面板的建议草稿尚未接入其持久机制，浏览器只留部分处理记录 | 新面板刷新/重登后继续编辑与权限/版本复核仍需实现，宜复用并扩展既有草稿能力 |
| 本地扩展验证滞后 | 近期以构建、Ruff/mypy、读取和健康检查为证据 | 静态门禁不足以证明混合执行、取消、异常恢复和真机链路 |
| 大量共享代码尚未提交 | API、Worker、模式配置、UI 与模型都有修改 | 需要划分可审查范围、冻结候选并记录迁移兼容，避免不可复现交付 |
| 文档口径存在漂移 | 本地说明仍写 SQLite 6/4、旧排除录制；新代码版本为 7 且已开放录制 | 应统一“当前范围”与“历史证据”，清理旧限制的当前式表述 |
| 领域边界再次耦合 | Hermes 记录目前位于 suite API，助手组件负责多类动作 | 应抽取命令生命周期与动作适配服务，继续遵循领域边界 |

## 5. 推荐后续路线及验收出口

以下是分析建议，不是已经执行或验收通过的任务。

| 顺序 | 工作包 | 依赖与验收出口 |
| --- | --- | --- |
| R0 | 支持范围与候选整理 | 建立当前功能矩阵和未提交改动清单，统一版本/支持口径；冻结可复现候选，提交推送按用户要求执行 |
| R1 | 可靠执行与恢复 | 共用命令/投递服务与资源身份保护，处理已记录但未投递、投递应答未知、重复确认、取消与重启；分别证明本地队列和 Celery 下不重复业务执行、不永久 pending |
| R2 | Windows 日常闭环验收 | API/Web/Android 混合串行套件、手动计划、报告/附件、失败转缺陷、取消/恢复；以真实测试目标和设备验证，保留模式边界 |
| R3 | 本地可转移交付与双模式 M8 | 新旧 SQLite、备份清单、异机恢复、缺依赖提示、会话切换和服务器回归；提供明确安装/启动交付清单，决定是否制作便携包 |
| R4 | Hermes 草稿与更多动作 | 持久草稿、确认时版本与权限检查、结果核对；稳定套件后扩展用例编辑、缺陷/知识，再推进真实模型生成和质量评测 |
| R5 | 单节点发布 C3.4/C3.5 | 可并行采集 SLO；最终发布依赖选定 SHA 的完整镜像、迁移、真实环境与稳定性证据 |
| 后续 | 多节点、iOS、外部供应商与高级 AI | 另立支持范围和目标环境验收，不挤占本地核心流程收口 |

其中，R1 是共用内核的优先事项；R2/R3 直接服务 Windows 日常使用与快速转移；服务器 SLO 采集可并行，但发布不能继承本地静态构建结论。
