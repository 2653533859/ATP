## 实现范围

承接 [N1.3 投递意图](suite-dispatch-development-2026-10-08.md)，本批将手动套件的消息身份头部接入本地队列和 Celery Worker。投递状态与运行结果仍分别保存，不将接受消息解释成执行成功。

| 环节 | 当前实现 |
| --- | --- |
| 身份核对 | 消息 task_id 必须等于投递 ID；运行 UUID、目标模式、运行编号、所属项目和加密参数须匹配 |
| 首次接受 | 意图 execution_token 为空、状态允许接受、当前同 UUID 运行仍 pending 时，条件更新接受记录；提交后才进入既有执行租约 |
| 重复消息 | 已有接受令牌即拒绝再次执行；UUID/参数不符或缺少必须头部也拒绝，不修改原运行 |
| 开始执行 | 再次核对 UUID，用 pending→running 条件更新裁决启动 |
| 既有租约 | 套件租约保存 UUID；租约冲突仍拒绝执行，不因到期重新启动原运行 |
| 结果保护 | 套件租约恢复只更新同 UUID 的非终态运行，保留已知终态；旧套件租约无 UUID 时不推断它属于当前编号 |
| 本地队列 | queued→running 条件更新并检查影响行数；保存投递 ID/运行 UUID，调用 task.apply 时传相同 task_id 和头部 |
| 拒绝回执 | Worker 返回固定 skipped 标记，本地队列记 skipped；不能因重复消息返回而将另一执行中的运行改成失败 |
| 查询 | 投递只读 API 增加 accepted_at；领取/接受令牌和加密参数仍不公开 |

接受令牌是永久的首次执行入口凭据，不是可到期抢占的执行租约。发布应答未知的消息也可以被有效 Worker 接受，接受后确认 submitted；迟到的发布失败不会覆盖此确认。

## 兼容与恢复边界

- 没有投递意图的计划/旧套件消息保留既有路由和租约，但读取当前 UUID并在开始时再次核对。已有意图的运行必须携带匹配头部，不能以旧消息绕过接受记录。
- 本地迁移仅按已有 created_at 对应关系补齐队列 UUID，再按 UUID 关联同模式意图；无法确认的记录不猜测绑定。其他用例、计划、Android 和性能消息未扩展为全域 UUID 接受机制。
- 本地仍只支持单 API/单 runner。条件领取防止重复选中同一行，不表示允许启动多个本地 ATP 进程；启动恢复流程未改造成多进程协调器。
- 接受后、取得租约前进程退出，运行可能仍 pending。接受记录会阻止重跑，但完整核对/取消交互仍待 N1.5；没有自动清除接受令牌或重新入队。
- 已开始但失联的执行仍可能有外部副作用。租约过期不触发第二次执行，也不承诺所有已在进行中的外部动作立即停止。全程写入隔离和副作用核对仍需后续验收。
- 旧套件租约 UUID 为空或与当前运行不符时保留拒绝，不自动填入当前 UUID。清理须先核对实际历史运行。
- 服务器须停止并核对执行流量后统一升级 API/Worker，应用 Alembic 0078；旧 Worker 不消费本批接受凭据，不将混用版本当作支持的发布方案。降级或恢复旧数据库前须停止/核对消息，避免接受记录丢失后旧消息再次执行。
